## Решения

- **Фото (п.7) делаются раньше входа (п.6)** (принято 2026-11-25). Storage пускает по сессии Supabase, и после смены входа фото перестали бы работать. Порядок: данные → фото → вход → скорость.
- **Вид загрузки для этапа 11** решается перед этапом 11. В `DESIGN.md` его нет. Этапы 9–10 от этого не зависят.

## Что учесть

- **Ядро нельзя переключать по таблицам.** `books`, `readings`, `sessions` и `goals` пишут друг в друга, и записи разошлись бы по двум базам.
- **Вход Supabase пока подходит.** UUID при импорте сохранены, поэтому до этапа 7 `user_id` берётся из текущей сессии.
- **Даты.** Драйвер отдаёт `timestamptz` как `2026-11-12 05:58:14.041+00`. Колонки приводятся к формату Supabase `2026-11-12T05:58:14.041+00:00` (этап 0).
- **Совместимость.** `better-auth` 1.7.28 по peer-зависимостям допускает Next 16, `drizzle-orm` 0.45.4 и `drizzle-kit` 0.31.11. Сборка и вход проверены на этапе 6.
- **Не сливать в `main` до деплоя дома:** push в `main` обновляет Vercel.

- **Отдельно, не в этой ветке плана:** в `src/lib/time.ts` границы дня и недели смещаются на час при переводе часов (найдено на этапе 3, ветка `fix/dst-boundaries`).

**Проверка после каждого этапа:** `npm run lint && npm run typecheck && npm run build`, затем `npm run start`. Переменные Supabase с этапа 7 не нужны.

## Данные (п.5)

### Этап 0. Фундамент, поведение не меняется

- **Что:** клиент БД (один экземпляр, подключение при первом запросе, чтобы сборка шла без `DATABASE_URL`); тип колонки `timestamptz`, отдающий ISO-строки; `requireUserId()` поверх `getCurrentUser()`; скрипт `typecheck`.
- **Файлы:** новые `src/db/index.ts`, `src/db/timestamptz.ts`, `src/lib/require-user.ts`; `src/db/schema.ts`, `package.json`.
- **Проверка:** `npm run db:generate` не создаёт миграцию; приложение работает как раньше.
- **До этапа 1 (владелец):** сохранить эталон из настроек: JSON, CSV книг и сессий, Markdown заметок. Если в Supabase появились данные после дампа, сначала сделать свежий импорт в пустые таблицы.

### Этап 1. Ядро, перенос один к одному

- **Что:** запросы на Drizzle, сигнатуры функций прежние.
  - В каждом запросе фильтр по `user_id`, при вставке он задаётся явно.
  - Перед вставкой по чужому `book_id` или `reading_id` проверяется владелец.
  - Где был `.single()`, пустой результат даёт ошибку.
  - Порядок `NULL` в сортировках сохраняется.
- **Файлы:** `src/lib/db/{books,readings,sessions,goals}.ts`, новый `src/lib/db/query.ts` (проверка владельца).
- **Проверка:**
  - Добавить книгу, начать и сохранить сессию, дочитать, перечитать, пауза и отказ, дедлайн, очередь, удаление. Изменения видны в `psql`.
  - Изоляция: добавить в `psql` второго пользователя с книгой. Её нет в списках, а `/books/<id>` отвечает «не найдено». Потом удалить его.
- **Временно:** главная, статистика, заметки и экспорт частично читают Supabase. Заметка к новой локальной книге не сохранится. Заметки, фото и OCR из локального приложения до этапов 4–5 пишутся в рабочий Supabase.

### Этап 2. Транзакции

- **Что:** смена полки, пауза, отказ, возврат, создание книги и сохранение, правка или удаление сессии вместе с `syncReadingCompletion` выполняются атомарно. Очередь обновляется одним запросом. Дневная цель и дедлайн пишутся через upsert. Транзакции записи одного пользователя выполняются по очереди (`userTransaction`, advisory lock). Запись сессии: `createSessionAndSync`, `updateSessionAndSync`, `deleteSessionAndSync`.
- **Файлы:** те же четыре и `query.ts`; `src/db/index.ts`, `src/app/session/actions.ts`, `src/app/sessions/[id]/edit/actions.ts`.
- **Проверка:** сценарии этапа 1; временная ошибка в середине транзакции не оставляет изменений; в очереди номера 1…N.

### Этап 3. Главная и статистика

- **Проверка:** главная, `/stats` во всех периодах, итоги года, прогноз и подсказки жанров. Цифры совпадают с запросами в `psql` и с продакшеном при тех же данных. Особо проверить границы дня и недели (Europe/Bucharest).

## Фото (п.7)

### Этап 5. Фото на диске

- **Что:**
  - Хранение в `PHOTOS_DIR/{user_id}/{note_id}.jpg`; без `PHOTOS_DIR` фото не сохраняются.
  - Маршрут `/api/photos/[noteId]`: проверяет вход и владельца, путь берёт только из базы, кэш приватный (1 час).
  - В адресе версия файла, поэтому после «Заменить» видно новое фото.
  - На сервере принимается только JPEG до 5 МБ. Запись через временный файл.
  - Фото уходит в Server Action файлом в `FormData`, а не base64: строку длиннее миллиона знаков React в аргументах отклоняет, одного `bodySizeLimit` мало. `bodySizeLimit` — 6 МБ.
- **Файлы:** `src/lib/db/{photos,notes,export}.ts`, `src/lib/{config,image}.ts`, `src/app/api/photos/[noteId]/route.ts`, `src/app/notes/actions.ts`, `PhotoNoteWizard`, `NoteEditorDialog`, `PhotoThumbnail`, `DataSection`, `next.config.ts`, `.env.example`, `.gitignore`. Удалён `src/lib/base64.ts`.
- **Проверка:** снять, сохранить, заменить, удалить; файл появляется и исчезает на диске; ZIP содержит фото; без входа фото не отдаётся. С телефона: port forwarding `localhost:3000` через `chrome://inspect`.
- **Нужно в `.env.local`:** `PHOTOS_DIR` с абсолютным путём вне проекта.
- **При переносе на домашний сервер:** скопировать файлы бакета `note-photos` в `PHOTOS_DIR` с теми же путями (в снимке от 2026-11-25 заметок с фото нет); включить `PHOTOS_DIR` в бэкапы.
- **Удаление книги** удаляет и файлы фото её заметок (с этапа 8). Файлы книг, удалённых раньше, остаются на диске.

## Вход (п.6)

### Этап 6. Better Auth рядом с текущим входом

- **Что:**
  - Таблицы `session`, `account`, `verification`.
  - Email с паролем и Google, регистрация закрыта, только `ALLOWED_EMAIL`: пользователь и вход для другого email отклоняются и на уровне базы Better Auth (`databaseHooks`).
  - UUID для id, вход на год с продлением раз в день, `nextCookies`, телеметрия выключена.
  - Без переменных входа сборка и приложение работают, а `/api/auth/*` отвечает 500.
  - `/api/auth/*` исключён из proxy уже здесь, иначе его не проверить.
  - Скрипт `npm run auth:set-password` задаёт пароль существующему пользователю и закрывает его прежние входы. `.mts`, чтобы Node запускал его без дополнительных пакетов.
- **Файлы:** `src/db/schema.ts`, `drizzle/0001_better_auth.sql`, `src/lib/auth.ts`, `src/app/api/auth/[...all]/route.ts`, `scripts/set-password.mts`, `src/proxy.ts`, `package.json`, `.env.example`. Новая зависимость: `better-auth` ~1.7.28.
- **Проверка:** миграция применяется; верный пароль проходит, неверный и регистрация отклоняются. Обычный вход пока прежний.

### Этап 7. Переключение входа

- **Что:**
  - Proxy проверяет настоящую сессию по базе, а не наличие cookie, и пускает только `ALLOWED_EMAIL`. Устаревшая cookie удаляется и ведёт на `/login` без цикла.
  - Сессию продлевает только proxy (раз в день, снова на год): серверные компоненты читают её без продления, потому что не пишут cookie.
  - `icon.svg` и `apple-icon.png` исключены из проверки.
  - Вход и выход через Better Auth в Server Actions. Способ входа для настроек берётся из cookie плагина `lastLoginMethod` (без миграции).
  - Google включается, только когда заданы `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, иначе кнопка скрыта. Одна переменная без другой вход не ломает.
  - Лимит пароля: 10 неудачных попыток за 15 минут, удачный вход обнуляет счётчик. Счётчик в памяти и не зависит от IP, поэтому работает при любой схеме деплоя; перезапуск сервера его обнуляет. Чужие email считаются отдельно. Кто знает email владельца, может временно закрыть новый вход (уже открытые входы работают).
  - `POST /api/auth/sign-in/email` отключён (`disabledPaths`): так нет второго пути к паролю с обходимым лимитом по `X-Forwarded-For`.
- **Файлы:** `src/proxy.ts`, `src/lib/{auth,get-current-user,login-rate-limit,config}.ts`, `src/app/login/{actions.ts,page.tsx,LoginForm.tsx}`, `src/app/settings/actions.ts`, словари, `.env.example`, `docs/DESIGN.md`. Удалены `src/app/auth/callback/`, `src/lib/request-origin.ts`, `src/lib/supabase/`.
- **Нужно в `.env.local`:** `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `ALLOWED_EMAIL`; пароль задан командой `npm run auth:set-password`.
- **Проверка:** вход паролем попадает в того же пользователя (все книги на месте); выход; сессия переживает перезапуск; приложение работает без переменных Supabase.
- **Не проверено:** настоящий Google (проверен с учебной заглушкой). Перед включением добавить в Google Cloud redirect URI `{BETTER_AUTH_URL}/api/auth/callback/google`.

### Этап 8. Аудит защиты

- **Что:**
  - Каждая Server Action начинается с `requireSignedIn()`: без входа переход на `/login`. Открыты только `login`, `signInWithGoogle` и `logout`. Новое действие должно начинаться так же.
  - Proxy не перенаправляет запросы Server Action: редирект из proxy браузер выполнить не мог, и вместо экрана входа был экран ошибки.
  - Все маршруты с данными, включая `/notes/export`, проверяют вход сами и отвечают 401. Proxy отвечает так же, а переход по ссылке в браузере ведёт на `/login`.
  - Запросы из браузера (поиск книг, распознавание, выгрузки) при 401 открывают `/login`.
  - Удаление книги удаляет файлы фото её заметок.
  - Удалены `@supabase/ssr` и `@supabase/supabase-js` (часть п.13).
- **Файлы:** `src/app/**/actions.ts`, маршруты `src/app/api/**` и `src/app/notes/export/route.ts`, `src/proxy.ts`, `src/lib/{require-user,unauthorized,leave-if-signed-out}.ts`, `src/lib/db/{books,photos}.ts`, `AddBookForm`, `PhotoNoteWizard`, `DataSection`, `package.json`.
- **Проверка:** все API без cookie дают 401. Запрос Server Action без cookie на любой путь ничего не меняет в базе и не отдаёт данные.
- **Осталось от Supabase:** папка `supabase/migrations/` и документы (`SETUP.md`) — история, на работу не влияют.
