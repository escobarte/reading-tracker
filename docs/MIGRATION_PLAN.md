## Решения

- **Фото (п.7) делаются раньше входа (п.6)** (принято 2026-11-25). Storage пускает по сессии Supabase, и после смены входа фото перестали бы работать. Порядок: данные → фото → вход → скорость.
- **Вид загрузки для этапа 11** решается перед этапом 11. В `DESIGN.md` его нет. Этапы 9–10 от этого не зависят.

## Что учесть

- **Ядро нельзя переключать по таблицам.** `books`, `readings`, `sessions` и `goals` пишут друг в друга, и записи разошлись бы по двум базам.
- **Вход Supabase пока подходит.** UUID при импорте сохранены, поэтому до этапа 7 `user_id` берётся из текущей сессии.
- **Даты.** Драйвер отдаёт `timestamptz` как `2026-11-12 05:58:14.041+00`. Колонки приводятся к формату Supabase `2026-11-12T05:58:14.041+00:00` (этап 0).
- **Совместимость.** `better-auth` 1.7.28 по peer-зависимостям допускает Next 16, `drizzle-orm` 0.45.4 и `drizzle-kit` 0.31.11. В работе ещё не проверено.
- **Не сливать в `main` до деплоя дома:** push в `main` обновляет Vercel.

**Проверка после каждого этапа:** `npm run lint && npm run typecheck && npm run build`, затем `npm run start`. Переменные Supabase нужны до этапа 7.

## Данные (п.5)

### Этап 0. Фундамент, поведение не меняется

- **Что:** клиент БД (один экземпляр, подключение при первом запросе, чтобы сборка шла без `DATABASE_URL`); тип колонки `timestamptz`, отдающий ISO-строки; `requireUserId()` поверх `getCurrentUser()`; скрипт `typecheck`.
- **Файлы:** новые `src/db/index.ts`, `src/db/timestamptz.ts`, `src/lib/require-user.ts`; `src/db/schema.ts`, `package.json`.
- **Проверка:** `npm run db:generate` не создаёт миграцию; приложение работает как раньше.
- **До этапа 1 (владелец):** сохранить эталон из настроек: JSON, CSV книг и сессий, Markdown заметок. Если в Supabase появились данные после дампа, сначала сделать свежий импорт в пустые таблицы.

### Этап 1. Ядро, перенос один к одному

- **Что:** запросы на Drizzle, сигнатуры функций прежние.
  - В каждом запросе фильтр по `user_id`, при вставке он задаётся явно.
  - Перед вставкой по чужому `book_id` или `reading_id` проверяется владелец.
  - Где был `.single()`, пустой результат даёт ошибку.
  - Порядок `NULL` в сортировках сохраняется.
- **Файлы:** `src/lib/db/{books,readings,sessions,goals}.ts`, новый `src/lib/db/query.ts` (проверка владельца).
- **Проверка:**
  - Добавить книгу, начать и сохранить сессию, дочитать, перечитать, пауза и отказ, дедлайн, очередь, удаление. Изменения видны в `psql`.
  - Изоляция: добавить в `psql` второго пользователя с книгой. Её нет в списках, а `/books/<id>` отвечает «не найдено». Потом удалить его.
- **Временно:** главная, статистика, заметки и экспорт частично читают Supabase. Заметка к новой локальной книге не сохранится. Заметки, фото и OCR из локального приложения до этапов 4–5 пишутся в рабочий Supabase.

### Этап 2. Транзакции

- **Что:** смена полки, пауза, отказ, возврат, создание книги и сохранение, правка или удаление сессии вместе с `syncReadingCompletion` выполняются атомарно. Очередь обновляется одним запросом. Дневная цель и дедлайн пишутся через upsert.
- **Файлы:** те же четыре; `src/app/session/actions.ts`, `src/app/sessions/[id]/edit/actions.ts`.
- **Проверка:** сценарии этапа 1; временная ошибка в середине транзакции не оставляет изменений; в очереди номера 1…N.

### Этап 3. Главная и статистика

- **Файлы:** `src/lib/db/{home,stats}.ts`.
- **Проверка:** главная, `/stats` во всех периодах, итоги года, прогноз и подсказки жанров. Цифры совпадают с запросами в `psql` и с продакшеном при тех же данных. Особо проверить границы дня и недели (Europe/Bucharest).

### Этап 4. Заметки, лимит OCR, экспорт

- **Что:** заметки и `ocr_usage` (атомарный счётчик) на Drizzle, затем экспорт. Файлы фото пока в Supabase.
- **Файлы:** `src/lib/db/{notes,ocr-usage,export}.ts`.
- **Проверка:** создание, правка, фильтры, избранное, теги, цитата дня. Выгрузки сравнить с эталоном. `grep -rli supabase src/lib/db` находит только `photos.ts`.

## Вход (п.6)

### Этап 6. Better Auth рядом с текущим входом

- **Что:**
  - Таблицы `session`, `account`, `verification`.
  - Email с паролем и Google, регистрация закрыта, только `ALLOWED_EMAIL`.
  - UUID для id, долгая сессия, `nextCookies`.
  - Скрипт, задающий пароль существующему пользователю.
- **Файлы:** `src/db/schema.ts`, новая миграция в `drizzle/`, новые `src/lib/auth.ts`, `src/app/api/auth/[...all]/route.ts`, `scripts/set-password.ts`; `package.json`, `.env.example`. Новая зависимость: `better-auth`.
- **Проверка:** миграция применяется; `curl`: верный пароль проходит, неверный и регистрация отклоняются. Обычный вход пока прежний.

### Этап 7. Переключение входа

- **Что:**
  - Proxy проверяет настоящую сессию, а не только наличие cookie, иначе возможен цикл редиректов.
  - `/api/auth/*` открыт; `icon.svg` и `apple-icon.png` исключены из проверки.
  - Вход, выход и способ входа в настройках через Better Auth.
  - Ограничение частоты попыток пароля: вызов из Server Action обходит встроенный лимит Better Auth.
- **Файлы:** `src/proxy.ts`, `src/lib/get-current-user.ts`, `src/app/login/{actions.ts,page.tsx}`, `src/app/settings/actions.ts`. Удалить `src/app/auth/callback/`, `src/lib/request-origin.ts`, `src/lib/supabase/`.
- **От владельца:** в Google Cloud добавить `http://localhost:3000/api/auth/callback/google`; в `.env.local` задать `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ALLOWED_EMAIL`.
- **Проверка:** вход паролем и Google попадает в того же пользователя (все книги на месте); чужой Google-аккаунт отклоняется; выход; сессия переживает перезапуск; приложение работает без переменных Supabase.

### Этап 8. Аудит защиты

- **Что:** явная проверка входа во всех Server Actions и Route Handlers в дополнение к фильтрам в данных. `/notes/export` без входа отвечает 401. Удалить `@supabase/*` (это часть п.13).
- **Файлы:** `src/app/**/actions.ts`, `src/app/notes/export/route.ts`, `package.json`.
- **Проверка:** все API без cookie дают 401. Запрос Server Action без cookie на путь вне proxy (например, `/icons/x`) ничего не меняет в базе.
